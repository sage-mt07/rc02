   1: # Advanced Rules（実務で効く要点）
   2: 
   3: ## Window と時間の扱い
   4: - 集計は UTC で統一する。
   5: - ウィンドウ長は要件から逆算する。
   6: - Final 出力を要する集計は遅延を許容する。
   7: 
   8: ```csharp
   9: // 例: 集計用ビューを宣言（概念例）
  10: modelBuilder.Entity<Candle>().ToQuery(q => q
  11:   .From<Tick>()
  12:   .Where(t => t.Symbol == "USDJPY"));
  13: ```
  14: 
  15: 要約: 時間は UTC、長さは要件基準で決める。
  16: 
  17: ## Push と DLQ の実務
  18: - ストリームは Push で購読する。
  19: - 想定外は DLQ を必ず確認する。
  20: - 再処理は修正後に再投入する。
  21: 
  22: ```csharp
  23: await ctx.Set<Event>().ForEachAsync(e => { /* use */ return Task.CompletedTask; });
  24: await foreach (var rec in ctx.Dlq.ReadAsync()) Console.WriteLine(rec.RawText);
  25: ```
  26: 
  27: 要約: 正常は Push、異常は DLQ を見る。
  28: 
  29: ## Avro と互換変更
  30: - 互換追加は許可し、破壊変更は避ける。
  31: - 追加は null 許容で安全に適用する。
  32: - 破壊変更は新トピックで移行する。
  33: 
  34: ```csharp
  35: public class Rate
  36: {
  37:   public string Symbol { get; set; } = "";
  38:   public decimal Price { get; set; }
  39:   public string? Source { get; set; } // 追加（後方互換）
  40: }
  41: ```
  42: 
  43: 要約: 追加は互換で、破壊は移行で処理する。
  44: 
  45: ## Table 化とキャッシュ
  46: - 参照用途は `.AsTable(useCache: true)` を選ぶ。
  47: - キャッシュは読み性能を安定化させる。
  48: - 変更頻度が高い場合は Stream を選ぶ。
  49: 
  50: ```csharp
  51: protected override void OnModelCreating(IModelBuilder b)
  52:   => b.Entity<RefData>().AsTable(useCache: true);
  53: ```
  54: 
  55: 要約: 参照は Table、頻繁更新は Stream を選ぶ。
  56: 
  57: ## CI での検証
  58: - 依存サービスを起動してからテストする。
  59: - 生成クエリはログで確認する。
  60: - 失敗時は DLQ とログを確認する。
  61: 
  62: ```bash
  63: docker-compose -f tools/docker-compose.kafka.yml up -d
  64: dotnet restore && dotnet test -v minimal
  65: curl -sf http://localhost:8088/info >NUL
  66: ```
  67: 
  68: 要約: 起動→テスト→疎通で安全に検証する。
  69: 
  70: ## 運用の注意（トピック管理）
  71: - 目的: 認識しないトピックの発生理由を理解し、削除/保持の判断を誤らない。
  72: - 前提: ksqlDB/Streams は内部処理用にトピックを自動作成する。
  73: 
  74: ### 典型的に自動作成されるトピック
  75: - シンクトピック: CSAS/CTAS の出力（例: `bar_1d_live`, `bar_1wk_final`）
  76: - リパーティション: `…-repartition`（結合/GroupByで使用）
  77: - チェンジログ: `…-changelog`（テーブルの状態保持）
  78: - ksqlDB システム: `_confluent-ksql-<service-id>_command_topic`, `_confluent-ksql-<service-id>_ksql_processing_log`
  79: - Schema Registry: `_schemas`
  80: - Kafka 内部: `__consumer_offsets`
  81: - 本ライブラリのDLQ（既定）: `dead-letter-queue`（`KsqlDsl.DlqTopicName`）
  82: 
  83: 注意: `__consumer_offsets`, `_schemas`, `_confluent-ksql-*` は削除しない。
  84: 
  85: ### 「消してよいか」の判断基準
  86: - 永続クエリが参照中か: `SHOW QUERIES;` で確認し、参照中なら削除しない
  87: - ストリーム/テーブルの存在: `SHOW STREAMS;` / `SHOW TABLES;` で対応する定義が残っていれば削除しない
  88: - 内部トピック（`-repartition`, `-changelog`）: 元の定義を `DROP … DELETE TOPIC;` で削除後に残存していないか確認
  89: - 消費者グループ: `kafka-consumer-groups.sh --describe --all-groups` に継続利用がないことを確認
  90: 
  91: 手順の原則: 削除は「TERMINATE（クエリ停止）→ DROP（DELETE TOPIC付き）→ 残存内部を確認」の順。
  92: 
  93: ### 保持期間（retention）設定の方法
  94: - Kafka CLI での変更（例）
  95:   - `kafka-configs.sh --alter --topic <topic> --add-config retention.ms=604800000`（7日）
  96:   - `kafka-configs.sh --alter --topic <topic> --add-config retention.bytes=1073741824`（1GiB）
  97:   - `kafka-configs.sh --alter --topic <topic> --add-config cleanup.policy=delete`（または compact）
  98: - DLQ の保持（アプリ設定例）
  99:   ```json
 100:   {
 101:     "KsqlDsl": {
 102:       "DlqTopicName": "dead-letter-queue",
 103:       "DlqOptions": { "RetentionMs": 604800000 }
 104:     }
 105:   }
 106:   ```
 107:   備考: 既存トピックの保持を変更する場合は Kafka CLI 側で調整する。
 108: 
 109: ### トピックの追跡・対応付けのコマンド
 110: - 一覧とフィルタ: `kafka-topics.sh --list | sort`
 111: - 詳細: `kafka-topics.sh --describe --topic <topic>`
 112: - ksqlDB 側の対応付け: `SHOW TOPICS;` / `DESCRIBE <stream|table>;`
 113: - クエリの停止: `TERMINATE <query-id>;` / 一括 `TERMINATE ALL;`
 114: - 定義の削除: `DROP STREAM/TABLE <name> DELETE TOPIC;`
 115: 
 116: 要約: システム/内部トピックは原則削除しない。削除は「クエリ停止→定義削除→内部残存確認→必要時のみ CLI で削除」の順で行う。retention は CLI もしくは DLQ 設定で管理する。
