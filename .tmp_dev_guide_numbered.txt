   1: # 開発者向けガイド (Dev Guide)   2:    3: このページはリンク集ではありません。ここを読めば最低限の方針・規約がわかり、すぐに手が動きます。詳細や根拠は必要に応じて各資料へ飛べますが、まずはここだけで完結します。   4:    5: ## 基本方針（3分で把握）   6: - 目的: C# で Kafka/ksqlDB を LINQ 的に扱うための DSL を提供する   7: - 優先: 読めるコード > 速い最適化（最適化は測定してから）   8: - 原則: 型安全・明示的な責務分離・例外は握りつぶさない   9:   10: ## プロジェクト構成（要点）  11: - `src/`: ライブラリ本体。名前空間は「責務で分ける」こと（Application/Query/Messaging 等）。  12: - `examples/`: 最小動作の実例。まずは hello-world を動かす。  13: - `tests/`: 単体テスト。DSL の入力→KSQL 生成の対応を重視。  14: - `tools/`: 開発・検証補助（docker-compose など）。  15:   16: ## コーディング規約（抜粋）  17: - 命名: パブリック API は意味のある英語名。略語は業界標準のみ（DLQ, DTO 等）。  18: - 例外設計: 入力検証は早期に失敗させる。再試行可能なエラーは呼び出し側へ明示。  19: - 非同期: I/O は `async/await` を徹底。同期ブロッキングを避ける。  20: - ロギング: エラーは StackTrace を保持。相関 ID をログに含める。  21: - フォーマット: 既存スタイルに合わせる。PR で自動整形が走る前提でズレを最小に。  22:   23: ## ログ運用（実務要点）  24: - ログ最小単位: 入力イベント、生成された KSQL、送受信結果。  25: - ID 設計: 同一トランザクションの相関 ID を貫通させる（例: `CorrelationId`）。  26: - 水準: `Information` 日常、`Warning` 回復可能、`Error` 要調査、`Critical` 直ちに通知。  27:   28: ## テスト方針（最小で効くところに当てる）  29: - 単体テスト: LINQ 入力 → 期待 KSQL のスナップショット比較。  30: - 物理テスト: `docs/physical_test_minimum.md` に沿って最小構成で疎通確認。  31: - 長期検証: バー系列（1d/1wk）でドリフトを検知。`docs/long_run_bar_validation.md` を参照。  32:   33: ## よくある落とし穴と回避策  34: - ksqlDB の Push/Pull の違いを取り違えない（購読 vs 取得）。  35: - Window 集計のタイムゾーン差異に注意（UTC で統一）。  36: - Avro スキーマ変更は後方互換を意識。破壊的変更はバージョン分岐。  37:   38: ## すぐに動かす（超短縮）  39: ```  40: git clone <repository-url>  41: cd rc02  42: dotnet restore  43: docker-compose -f tools/docker-compose.kafka.yml up -d  44: cd examples/hello-world  45: dotnet run  46: ```  47:   48: ## さらに深く知る（必要になったら）  49: - API リファレンス: `docs/api_reference.md`  50: - 設定リファレンス: `docs/docs_configuration_reference.md`  51: - 高度なルール: `docs/docs_advanced_rules.md`  52: - トラブル対応: `docs/troubleshooting.md`
